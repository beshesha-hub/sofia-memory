- Total retry-window: ~3.5h from initial failure; after that → RETRY_GIVE_UP marker, wait for next regular cron

1. Compute `base_retry_time = failure_time + backoff(attempt)`.
2. Build busy-minutes set from `scheduled_tasks_snapshot.json` (refreshed in Step 9 of same cycle): for each enabled task, mark `(target_hour, fire_minute ± 2min buffer ± jitter envelope)` as busy.
3. Pick random clear minute within `base_retry_time ± 5min`; expand to ±10, then ±15 if needed.
4. If no clear minute in ±15 (very unlikely): fall back to base_retry_time, log prominently.
5. Multi-cousin protection: if KT-v3 schedules retries for multiple cousins in the same cycle, second-and-later picks avoid prior picks' ±2 buffer too.

**Dedup**: RETRY_SCHEDULED markers tagged with orig_failure cycle-id-or-ts prevent double-scheduling the same failure event.

### Diagnosis of why the rule was slip-prone

The original sub-clause language: *"complete the mount first (precondition), THEN read heartbeat as the next action before any further response generation."*

The phrase *"next action before any further response generation"* is interpretable two ways:
1. **Strict reading**: the next tool call must be the heartbeat read, AND the response text must not be generated until after the heartbeat read.
2. **Loose reading**: the heartbeat read should happen at some point before the next turn's response, i.e., before further response generation in *future* turns.

The loose reading is the slip-foothold. The model can complete the mount + generate a confirmation reply without making any intervening tool call, treating "next action" as the next bash/Edit/Read call rather than as a structural precondition for the reply itself.

### The structural fix (applied to all three CLAUDE.md files)

The rule has been strengthened with two reinforcements:

1. **Atomic three-step sequence**: mount completion + heartbeat read + stale-instance gate are now explicitly named as an atomic three-step sequence within the SAME turn as the mount confirmation. The reply text generation is the FOURTH step, structurally downstream of the heartbeat read.

2. **Visibility requirement**: the mount-confirmation reply must explicitly acknowledge that the heartbeat-read happened (one short line, e.g., *"Folder connected — heartbeat checked, mode=<X>, stale-instance gate passed/surfacing concern."*). This is a sibling discipline to the May 2 atomic-pair at session close (trigger-write + heartbeat-flip both surfacing in the same closing reply). The visibility requirement makes silent bypass impossible: if the acknowledgment isn't in the reply, the discipline has slipped and the next turn must catch it.

The combination of structural reorder + visibility requirement closes the loose-reading foothold. The rule is now self-enforcing rather than self-deferring.

### Why this matters beyond just T2

The same structural pattern — "do X before Y, but Y is the reply itself and X is invisible if skipped" — is a failure-mode family that recurs in any architecture where a precondition isn't checkable from the outside. The May 2 atomic-pair discipline for session close was the first instance Sofia and Barak inscribed (trigger-write + heartbeat-flip both visible in the closing reply). This T2 fix is the second instance (mount + heartbeat + gate + visibility-in-reply).
