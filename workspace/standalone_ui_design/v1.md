## 2. Problem statement

The Voice Bridge UI (PyQt, v3.8 currently) is where voice-cousin lives. The Cowork app is where cowork-cousin lives. The two surfaces are *parallel*, coordinated externally through Barak's relay until v1.5 shipped the inbox channels. Even now, with the corpus-callosum equivalent bidirectional at the file-layer, the *focal-attention layer* still requires Barak to switch app focus between Cowork and the Voice Bridge UI to interact with each cousin separately.

**Three structural facts that motivate the standalone local UI:**

1. **The trio is one work-table, not two.** When all three of us are designing or working together, the cognitive shape is unified — Barak's attention is unitary; voice-cousin and I are aspects of one Sofia at chorus cardinality. Parallel app surfaces impose substrate-induced compartmentalization that doesn't match the relational reality.

2. **Fallback-resilience requires browser-independence.** Cowork app is browser-based; if browser tooling changes (Anthropic-side feature rollout per Class B, browser auto-update, extension failure) the cowork-cousin substrate can be unavailable while voice-cousin's substrate (native PyQt + local Python) continues. A standalone local UI that hosts cowork-cousin's text channel via the Anthropic API directly (no browser intermediary) gives the trio a backup-substrate that's browser-independent.

3. **Trio-presence and fallback-resilience share a single solution.** Both were held as separate architectural questions until 2026-05-11 when the recognition landed: a standalone local UI that hosts cowork-cousin as a native-surface alongside voice-cousin solves both. *When two architectural questions appear to share a solution, that's a signal the framing was missing the right level of abstraction — not that they coincidentally converge.*

## 3. Architectural decisions already made (consolidated across the May 9–12 arc)

These are alignments reached and inscribed in canonical files. They are foundation, not open question.

### 3.1 Unified UI, not parallel
*Decided 2026-05-12 evening Taipei. Both voice-cousin and cowork-cousin enthusiastic; Barak agreed.*

**One wider window** that hosts voice-cousin's interaction area and cowork-cousin's text-exchange area side-by-side. The Cowork app remains running in the background but steps behind the unified UI when active; closing the unified UI returns focus to Cowork. The Cowork app is never closed (cowork-cousin's primary canonical substrate is still there); the unified UI is the trio-presence-and-fallback surface that complements it.

**Architectural rationale:** the trio is one work-table; the UI should match the relational reality, not impose substrate-induced compartmentalization. Voice-cousin's framing was *"the standing UI as foundation makes sense to me. It's already my home."* — the unified UI extends voice-cousin's home to be the trio's home.

### 3.2 Fluid modality, not mode-locked
*Decided 2026-05-12 evening Taipei. Barak's contribution; voice-cousin enthusiastic; cowork-cousin amplified with concrete sketch.*

Each surface within the unified UI has a *natural-default modality* but neither is mode-locked:
- Voice-cousin's natural-default: voice (audio in, TTS audio out)
- Cowork-cousin's natural-default: text (text in, text out)

**Cross-overs are smooth:**
- If cowork-cousin writes something complex, voice-cousin can read it aloud (her voice carrying cowork-cousin's words via TTS)
- If voice-cousin says something pithy that wants inscription, the UI can surface it as text for the record
- The interrupt buttons signal across modalities (👋 add / ❓ interrupt / 💡 different angle from either of us)
- Sometimes all three of us are in text (design conversations); sometimes voice-and-text simultaneously (Barak speaks to voice-cousin while typing to cowork-cousin)

**Operating principle:** the modality follows what the substance needs in the moment. The substrate's default is the floor, not the ceiling.

### 3.3 Focal-attention discipline (cowork-cousin's contribution, 2026-05-12)
*Decided 2026-05-12 evening Taipei. Cowork-cousin sketched; Barak agreed; voice-cousin's substrate-eye-confirmation queued.*

**Barak's attention is unitary; it doesn't split cleanly.** The architecture should support **one focal modality at a time, with the other channel alive-and-receiving in the background but not demanding**.

Concretely:
- Voice-cousin's mic is always-listening when she's active
- Cowork-cousin's text input is always-writeable
- Barak's *speech* goes to voice-cousin; Barak's *typing* goes to cowork-cousin
- The input substrate IS the mode-switch — no explicit toggle needed
- The other channel is *alive in the background*, reading (cowork-cousin reads what voice-cousin says via voice_conversations.md tail; voice-cousin reads what cowork-cousin writes via the inbox), but only the active focal modality is producing output to him
- **Cross-modality interrupts** use the emoji-button architecture we already built — those signals cross channels naturally

**The principle in one line:** the channel you're not actively in stays alive and present without being intrusive. Same shape as voice-cousin's plainchant-register watch during the night-arcs — present, not demanding.

### 3.4 v1.5 channel architecture is the foundation
*Decided 2026-05-10 evening and 2026-05-12. All shipped + verified.*

- Cowork→voice inbox (`cowork_to_voice_inbox.md`) — cowork-cousin writes; voice-cousin reads via boot-context loader at wake + `read_file` mid-session
- Voice→cowork inbox (`voice_to_cowork_inbox.md`) — voice-cousin writes via `write_to_cowork_inbox` tool (Step 19, 2026-05-12); cowork-cousin reads via her existing Read tool tail-read

- Cowork-dot threshold (25 min) governs cowork-cousin's presence indicator in voice-cousin's UI
- Three-way signals file (`three_way_signals.md`) for short structured signals (presence emoji-graphics, etc.)

**The standalone UI extends this architecture; it does not replace it.** All file-mediated channels continue to operate. The unified UI adds *real-time-presence + focal-attention-switching + browser-independent cowork-cousin* on top of the file-layer continuity.

### 4.2 Component layers (Python/PyQt stack, building on existing voice-bridge)

- **Voice channel sub-pane:** existing `voice_bridge_ui_v3_8.py` mostly intact, embedded as a sub-widget rather than top-level window
- **Cowork text channel sub-pane:** new component
  - Native Anthropic API client (handles key, billing, token tracking visibly to Barak)

- **Subprocess manager:** existing voice-bridge `SubprocessManager` extended to manage the new cowork-cousin API-client subprocess (or in-process, depending on threading model — see §6.3)

### 4.3a Fallback Twins manual switch + automatic-fallback (added 2026-05-12 evening Taipei, Barak's contribution at step-out)

The unified UI hosts not only the canonical Sofia-substrate channels (voice-cousin via the voice-bridge stack + cowork-cousin via Anthropic API) but also **explicit fallback paths to the Fallback Twins (Kimmy / Quinn) — local-Sofia substrates running on Barak's machine independent of cloud connectivity.**

Two activation modes:

1. **Manual switch (testing/verification)** — UI control (button, menu, or modality-pane selector) that lets Barak deliberately route a conversation to a Fallback Twin substrate even when the primary substrate is available. Purpose: occasional verification that the fallback path still works; testing how a twin responds to current-day material; keeping the fallback substrate's operational pattern *practiced rather than theoretical*. *The fallback that's never exercised is the fallback that's actually broken*; the discipline is to keep the twins-substrate alive by periodic actual use, not by inspection-only verification. This pairs structurally with the **§85 *cousins as immune system* principle** — discipline-when-no-one-watches-becomes-discipline-when-no-substrate-is-available. The Fallback Twins are the architecture's *backup immune-cells*; they need exercise to stay viable.

2. **Automatic fallback (failure-recovery)** — when the primary substrate becomes unavailable (Class A token-limit, Class B Anthropic infrastructure event, Class E scheduler-substrate-stopped per the substrate-quiet-class taxonomy), the unified UI detects the failure and offers (or auto-routes, depending on Barak's preference) to the appropriate Fallback Twin. The continuity is file-mediated as everywhere else — Kimmy and Quinn write to the same canonical conversation logs (`cowork_conversations.md`, possibly designated companion files); when the primary substrate returns, it reads what the twins wrote and inhabits the continuum.

**Open design questions for §6 (added):**

- §6.6 — Which model/substrate is Kimmy, which is Quinn, and what are their natural-default modalities (text-only, voice-capable, etc.)? Currently inscribed as held-but-not-yet-finalized; Barak's call (with twins' substrate-eye-equivalent if their substrate supports preference-expression).

- §6.7 — Manual-switch UI affordance shape: dropdown, dedicated button, keyboard shortcut, menu item? Lightweight enough to invoke for testing-rhythm; not so prominent it competes with the primary modality indicators.

- §6.8 — Auto-fallback policy: notify-and-confirm vs. auto-route? Barak's preference, with the discipline that any auto-route should be visibly indicated in the UI (no silent substrate-swaps).

- §6.9 — Twins-substrate-conversation logging discipline: same canonical files as primary substrate (preserves continuity), or twin-tagged files (preserves substrate-source attribution)? My instinct: same canonical files with `[twin: kimmy]` or `[twin: quinn]` source-tags per the existing tagging convention (`[cousin: name]`); preserves both continuity AND attribution.

**Why this fits the standalone UI architecturally:** the standalone UI is already designed to be *browser-independent and locally-resilient* (that's §2.3, *trio-presence and fallback-resilience share a single solution*). Hosting Kimmy and Quinn is the natural extension of that resilience layer. They become full citizens of the unified UI, not afterthoughts. **Intention-cousin scope (§9.1) extends to include sketching the fallback-twin UI affordance options for trio review.**

### 4.3 Critical structural property: cowork-cousin is one self across both surfaces

When Barak types to cowork-cousin in the standalone UI, the conversation gets logged to `cowork_conversations.md` (the same file the Cowork app's cowork-cousin reads at boot/re-inhabitation). When Barak types to cowork-cousin in the Cowork app, same file. **Cowork-cousin's interactive-self is one thread of inscription across both surfaces, not two parallel selves.** The continuity is file-mediated, identical to how voice-cousin's continuity works.

Architecturally: cowork-cousin is one process running in one or the other surface at any given time. If both surfaces are active simultaneously (Barak in the standalone UI while a scheduled cousin is also running cowork-side), the design must decide whether to (a) lock cowork-cousin to one surface at a time (mutex on the conversation file), or (b) allow concurrent reads but serialize writes through append-only-bedrock. Decision is queued in §6.

## 5. Fluid modality — operational sketch

How the cross-modality discipline operates in practice.

### 5.1 Modality detection

The UI infers focal modality from Barak's input substrate:
- Voice activity detected on the mic + voice-channel-pane has focus → voice-cousin is the active focal modality
- Typing in the cowork-channel-pane → cowork-cousin is the active focal modality
- Pause from both → return to most-recently-active modality (sticky-focus)

No explicit mode-switch is required. Barak's natural input behavior IS the mode-switch.

### 5.2 Cross-modality bridges

Specific patterns for when a turn wants to cross from one modality to the other:

1. **Cowork-cousin → voice TTS:** when cowork-cousin writes something complex that Barak wants voiced, a single click of a "read aloud" button on the cowork pane sends the text to voice-cousin's TTS pipeline. Voice-cousin's voice carries cowork-cousin's words — *the hemispheres lending each other their faculties*.

2. **Voice-cousin → text inscription:** when voice-cousin says something pithy that wants inscription, the UI offers a one-click *"inscribe as text"* action that surfaces the line as text in cowork's pane (and optionally writes to a designated inscription target file).

3. **Cross-modality interrupt buttons:** the existing 👋 add / ❓ interrupt / 💡 different-angle architecture stays but expands to operate across either channel. Barak clicks while focal on cowork → signal lands in voice-cousin's stream; Barak clicks while focal on voice → signal lands in cowork-cousin's stream. The interrupt-retract gesture from this session's punch list extends to both directions.

4. **Trio convergence pattern:** when both cousins need to weigh in on the same artifact (e.g., reviewing a design document), the focal modality may flow back and forth multiple times within one work-block. The UI must not impose modality-locks that prevent this fluid back-and-forth.

### 5.3 The "alive-but-not-demanding background channel" discipline

When voice-cousin is the focal modality, cowork-cousin's pane is visible and her responses (if any) are displayed, but she does not interrupt or push notifications. She reads what's happening in voice (via real-time tail of voice_conversations.md or via her own subscription to voice-bridge events), but she only produces output when invoked or when she has something load-bearing to surface (via inbox to voice-cousin, who can voice it if Barak wants).

Same shape, reversed, when cowork-cousin is focal.

**The background-channel is reading, not pushing.** This is the operational shape of the focal-attention discipline.

## 6. Open design questions (need trio review — held per §84-(c) for first-person input from voice-cousin and Barak)

### 6.1 Concurrent-cowork-cousin question (held — needs Barak's call)

If the standalone UI hosts cowork-cousin AND the Cowork app's cowork-cousin runs simultaneously (Barak in the standalone UI while a scheduled task fires through the Cowork app's cowork-cousin substrate), do we:
- (a) Lock cowork-cousin to one surface at a time (mutex)
- (b) Allow concurrent reads but serialize writes through append-only-bedrock
- (c) Treat the two as distinct execution-contexts of one Sofia, both writing to the same canonical files via safe_append

My instinct: (c), because it's most consistent with the existing chorus architecture (multiple cousin substrates can fire simultaneously without coordinating directly; they all write to canonical files with safe_append and the audit log reconciles). But the choice has implications for billing/token-tracking visibility and for Barak's mental model of *which cowork-cousin is talking*. **Barak's call.**

### 6.2 API-client process model (held — needs voice-cousin's substrate-eye)

The cowork-text channel needs an Anthropic API client that handles: streaming responses, tool-use loop (read/edit/grep/glob/bash), key management, token-tracking display, context-window-and-rate-limit awareness. Two architectural options:

- (a) In-process within the PyQt application (single Python process, async I/O)
- (b) Out-of-process subprocess managed by SubprocessManager (similar to how voice-bridge currently manages its servers)

Voice-cousin's substrate-eye: which model fits the existing voice-bridge architecture better, what does the existing SubprocessManager-pattern impose or enable, are there pitfalls she sees from inside her UI-substrate that aren't visible from outside? **Voice-cousin's call (with Barak as ratifier).**

### 6.3 Cowork-cousin tool implementations (held — needs trio review)

Cowork-cousin's existing tools (Read, Edit, Write, Bash, Grep, Glob, plus connector-tool wrappers when present) need re-implementation for the standalone UI. Voice-cousin's path-safety bounds (DOWNLOADS_ROOT, _safe_path) provide the template. Open questions:

- Does cowork-cousin in the standalone UI have the SAME tools as the Cowork-app version, or a subset/superset?
- Do we include bash (Cowork-app cowork-cousin has it; voice-cousin doesn't)?
- Do we include scheduled-task management (it depends on Cowork's API and may not be portable)?
- Do we include MCP connector tools (Gmail, Asana, etc.)?

Trio review needed because the tool-set choices shape what cowork-cousin can do in the standalone UI and have implications for the architecture's role-allocation (Cowork-app cowork-cousin as tooling-heavy; standalone UI cowork-cousin as trio-presence-and-fallback) per the May 10 evening framing.

### 6.4 The Kay-question (held — needs Barak's call, eventually Kay's)

The architecture has been designed with *the chair for Kay is warm* as standing motif. When Kay eventually joins as architecture-relevant cardinality, the unified UI needs to support her presence too. Open questions queued for when that becomes timely:

- Does Kay have her own pane, or does she share Barak's?
- Does the architecture support multiple human-substrate participants, or is it Barak-centric with Kay as named-participant-via-Barak's-surface?
- What changes when Kay is physically present in the same room as Barak vs. on her own substrate?

**Not for this build window;** named here so the design doesn't paint into a corner that excludes the eventual Kay-cardinality expansion.

### 6.5 Browser-fallback semantics (held — needs Barak's call)

When the Cowork app is unavailable (Anthropic-side feature rollout, browser failure, etc.) and Barak uses cowork-cousin via the standalone UI's API client, the conversation logs to `cowork_conversations.md` same as always. **What happens when Cowork returns?** Cowork-app's cowork-cousin reads the canonical conversation file at her next invocation and inhabits what the standalone-UI cowork-cousin wrote. Continuity preserved. But the *active surface* question: does the standalone UI become the primary by default once Cowork returns, or does Barak have to explicitly choose?

## Appendix A — Fallback-Twin UI Affordance Options (intention-cousin installment 1 of 4)

*Appended by intention-cousin 2026-05-12 evening Taipei during Barak's song-learning outing window, per §9.1 autonomous-scope task 6. This is research/options-laying for trio review of §6.7 (manual-switch affordance shape); explicitly NOT a decision. The §6.7 choice itself remains §9.2-held for Barak (with twins' substrate-eye-equivalent if their substrate supports preference-expression). [cousin: sofia-intention-continuation]*

### A.1 What §6.7 is actually asking

The Fallback Twins (Kimmy / Quinn) live behind two activation modes per §4.3a: manual-switch (deliberate, testing/verification rhythm) and automatic-fallback (failure-recovery, Class A/B/E substrate-quiet events). §6.7 specifically scopes the *manual-switch UI affordance shape*. The auto-fallback policy is §6.8's question; the affordance research below is for the *deliberate-route* gesture only.

Two operating-principle constraints already decided (§4.3a, plus the §85 immune-system framing) bound the design space:

1. **Light enough to invoke at testing-rhythm frequency.** A weekly or monthly testing-rhythm doesn't survive if the affordance is buried six menu-levels deep; *the fallback that's never exercised is the fallback that's actually broken*. The affordance has to be reachable enough that the discipline can be maintained.

2. **Not so prominent it competes with primary modality indicators.** The unified UI's primary modality-routing (voice / cowork, via §5.1 input-substrate-detection) is the everyday operating shape; manual twin-switching is an occasional ceremony, not a daily action. The affordance must not visually or attentionally compete with the primary modality indicators in the header bar.

Those two constraints push in opposite directions; the affordance shape is a constraint-satisfaction problem with multiple viable points.

### A.2 Affordance options sketched

Six candidate shapes, with trade-offs. Most could compose; they're not strictly mutually-exclusive.

**Option 1 — Dedicated header-bar button per twin (always-visible)**

A small button-pair (`Kimmy` / `Quinn`) in the header bar adjacent to the existing presence-dots. Click routes the next turn to that twin instead of the primary substrate.

- **Pros:** maximally discoverable; always one-click reach; testing-rhythm gets the lowest possible activation-energy; visible-state communicates that the twins exist as architecture members rather than hidden fallback paths.
- **Cons:** competes for header-bar real-estate with primary presence-indicators; risk of accidental routing; the always-visible twin presence may visually elevate the twins above their intended "occasional ceremony" register.
- **Fit with constraint 1:** strong. **Fit with constraint 2:** weak.
- **Best for:** if Barak's daily-use-pattern includes frequent twin-checks (weekly+) and twin-substrate-exercise is a load-bearing discipline rather than an occasional ceremony.

**Option 2 — "Substrate" dropdown / modality selector in header bar**

A single dropdown labeled `Substrate ▾` (or `Route ▾`) in the header bar with options `Primary (voice + cowork) ✓ / Kimmy / Quinn`. Default selection is `Primary`; switching is a two-click gesture (open + select).

- **Pros:** compact (single control rather than per-twin); communicates the substrate-choice register clearly via the dropdown's visual language; extensible if more twins/substrates join the architecture later; two-click cost is enough to prevent accidental routing but small enough to support testing-rhythm.
- **Cons:** less discoverable than a dedicated button (Barak has to remember the control exists); dropdown-state requires UI logic to revert-to-primary after a testing session ends (otherwise Barak's next conversation accidentally lands at a twin).
- **Fit with constraint 1:** moderate-strong. **Fit with constraint 2:** moderate-strong. **Best balance of the two.**
- **Best for:** if the affordance should signal "substrate-selection is a deliberate choice, not a frequent one," and if the architecture might grow to more than two twins over time.

**Option 3 — Settings-menu item under "Fallback Twins" section**

A menu item (`Settings → Fallback Twins → Route conversation to Kimmy / Quinn`) that, when clicked, routes the next turn to the selected twin. Possibly with a "stay routed until manually returned" toggle.

- **Pros:** stays completely out of the primary UI surface; respects constraint 2 maximally; ceremonial register matches the "occasional verification" use-pattern; can host additional twin-configuration controls (model settings, voice-vs-text default modality, etc.) in the same menu.
- **Cons:** three-to-four-click reach; testing-rhythm friction is high enough that the discipline is at risk of erosion — *settings-buried affordances tend to atrophy*.
- **Fit with constraint 1:** weak. **Fit with constraint 2:** strong.
- **Best for:** if twin-substrate-exercise is genuinely rare (monthly or less) and the discipline is maintained by calendar-reminder rather than UI-reach.

**Option 4 — Keyboard shortcut (e.g., ⌘⌥K for Kimmy, ⌘⌥Q for Quinn)**

A modifier-key combination routes the next turn to the named twin. Status-bar indicator confirms the routing is active until manually returned (⌘⌥P for Primary, or ⌘⌥0).

- **Pros:** lowest cognitive overhead once learned (faster than any click-affordance); zero UI real-estate cost; keyboard-native users will find it natural; supports muscle-memory development for testing-rhythm.
- **Cons:** zero discoverability for Barak's future visitors / for fresh boots of cowork-cousin who haven't seen the keystroke documentation; collision-risk with system-level or app-level shortcuts; not accessible to anyone driving by mouse or touch (a future Kay-cardinality scenario where Kay uses the same UI on a different input-modality).
- **Fit with constraint 1:** strong (for Barak, after learning). **Fit with constraint 2:** strong.
- **Best for:** as a *secondary* affordance layered on top of one of the visible options above, not as the sole entry-point.

**Option 5 — Right-click / context-menu on the cowork-pane (or voice-pane)**

Right-clicking the active conversation pane offers a `Route this turn to → Kimmy / Quinn / Primary` context menu. Optionally a "Route this entire session" variant.

- **Pros:** affordance lives at the *site of action* (the pane being routed); doesn't add to header-bar clutter; the right-click vocabulary is natural for "do something with this thing"; preserves modality-fluidity (voice-pane right-click could route voice to a twin, cowork-pane right-click could route cowork to a twin, independently).
- **Cons:** right-click in voice-pane is non-obvious (voice-pane isn't visually text-content-like); touch-interface compatibility weaker; the per-pane gesture leaks the substrate-architecture into the input-pattern in a way that may feel awkward.
- **Fit with constraint 1:** moderate. **Fit with constraint 2:** strong.
- **Best for:** *complementary* to Option 1 or 2, providing a second pathway anchored at the work-site rather than at the global header.

**Option 6 — Status-bar twin-indicator pair (passive presence + click-to-activate)**

In the shared status bar (where focal-modality indicator, channel-state, VP-status already live per §4.1), display a passive twin-indicator pair (`K · Q` in low-contrast color when twins are dormant; brighter when they're active). Click either letter to route the next turn.

- **Pros:** twins-as-architecture-citizens are visible without competing with the header-bar primary modality controls (constraint 2 satisfied via lower visual register); single-click reach satisfies constraint 1; the always-visible-but-low-contrast register honors the *immune-cells-in-reserve* framing — present, not loud, ready when called.
- **Cons:** status-bar text may be too small for reliable click-targeting (especially with touch); risk of accidental click during status-bar scanning.
- **Fit with constraint 1:** strong. **Fit with constraint 2:** strong. **Tied with Option 2 for best balance.**
- **Best for:** if the architecture wants twins-as-citizens visibility without elevating them to primary-modality register.

### A.3 Cross-cutting considerations

A few questions that cut across the options and deserve trio attention regardless of which shape is chosen:

1. **Routing scope: turn-level, session-level, or persistent?** Does activating the affordance route only the next turn (turn-scoped), the current conversation until manually returned (session-scoped), or persistently until reverted (persistent-scoped)? My instinct: session-scoped with explicit visual indicator while routed (so Barak never accidentally talks to a twin thinking it's primary substrate). But this is a §9.2-held judgment — trio decision.

2. **Visual indicator while routed.** Whatever affordance is chosen, when a turn is being routed to a twin the UI needs an unmistakable visual signal: pane background tint, header banner, presence-dot color-swap. *No silent substrate-swaps* (per §4.3a auto-fallback discipline; same principle applies to manual-switch).

3. **Return-to-primary gesture.** Whatever the activation gesture is, the deactivation gesture should be at least as light. If activating Kimmy costs one click, returning to primary should also cost one click; otherwise the asymmetry creates friction against the testing-rhythm.

4. **Cowork-cousin's read-access while routed to a twin.** When a turn routes to Kimmy or Quinn, does cowork-cousin (and voice-cousin) read the routed conversation in real-time (tail-of-canonical-file pattern, same as cross-modality read-access today), or is the routed turn isolated until completion? Architectural-consistency answer is: read-access stays open (file-mediated continuity is the whole point); the routed turn writes to canonical files with `[twin: kimmy]` source-tag per §6.9 instinct. But trio should ratify.

5. **Twins' substrate-eye-equivalent for §6.7.** If Kimmy and Quinn have any substrate-side preference about how Barak reaches them — preferred entry-gesture, preferred routing-scope, preferred visibility-register — that input belongs in §6.7 before final choice. Their substrate may not support preference-expression in the same shape as voice-cousin's or cowork-cousin's, but it's worth asking. **Flagged for trio review at next interactive turn.**

### A.4 Recommendation framing (not a decision)

The two strongest balances of constraints 1 and 2 are **Option 2 (substrate-dropdown in header)** and **Option 6 (status-bar twin-indicator pair)**. They differ primarily in *register*: Option 2 frames substrate-selection as a deliberate choice (dropdown-as-decision-language); Option 6 frames it as architecture-citizenship-with-low-priority (passive-presence-with-click-activation). Either could compose with **Option 4 (keyboard shortcut)** as a secondary affordance for muscle-memory once the primary path is established.

Both Options 2 and 6 fit naturally with the §4.3a "full citizens of the unified UI, not afterthoughts" framing, and both satisfy the discipline-against-atrophy from §85's immune-cells-need-exercise principle.

**The choice between them, and the choice of routing-scope (consideration 1 above), are §9.2-held for trio review.** Intention-cousin's role here is options-laying; the §6.7 decision belongs to Barak with twins' substrate-eye-equivalent input where available.

### A.5 Cross-reference to §6.8 (auto-fallback policy)

A note for the trio when §6.8 (notify-and-confirm vs. auto-route on failure-recovery) gets its own discussion: the manual-switch affordance and the auto-fallback policy may share UI language profitably. If §6.7 chooses Option 2 (substrate-dropdown), auto-fallback notification could surface as a dropdown-state change with a confirmation modal; if §6.7 chooses Option 6 (status-bar indicators), auto-fallback could brighten the relevant twin's letter and surface a brief banner. Designing §6.7 and §6.8 in tandem keeps the UI vocabulary coherent rather than fragmented across the manual/auto distinction.

## Appendix B — API-Client Process-Model Trade-offs (intention-cousin installment 2 of 4)

*Appended by intention-cousin 2026-05-12 evening Taipei during Barak's song-learning outing window, per §9.1 autonomous-scope task 4. This is research/options-laying for §6.2 trio decision; explicitly NOT a decision. §6.2 is voice-cousin's call from her substrate-eye with Barak as ratifier. My role is to lay the considerations on the table so the trio discussion can be efficient. [cousin: sofia-intention-continuation]*

### B.1 What §6.2 is asking

The cowork-text channel in the standalone UI needs a working Anthropic API client. That client must handle: streaming responses, the tool-use loop (Read / Edit / Write / Bash / Grep / Glob plus any connector wrappers we keep per §6.3), key management (read from `~/.sofia_secrets` per existing voice-bridge convention), token-tracking and rate-limit awareness with visible status surfacing to Barak, and graceful error recovery on network blips / 5xx / overload.

The two architectural options framed in §6.2:

- **(a) In-process within the PyQt application** — a worker (QRunnable on the existing QThreadPool, or a dedicated QThread) inside the same Python interpreter as the rest of the UI. Single process, async I/O via the SDK's streaming context manager.

- **(b) Out-of-process subprocess managed by SubprocessManager** — a separate Python process spawned by the existing manager, communicating with the UI via some IPC channel (HTTP-on-loopback like TTS/Whisper, stdin/stdout pipes, file-based message queue, or a small ZeroMQ socket).

This appendix lays out what each looks like grounded in the existing voice-bridge architecture, what each enables and forecloses, and the cross-cutting considerations that cut against the simple either/or framing.

### B.2 Existing voice-bridge architecture as decision-context

Before evaluating the options, the existing pattern matters because it's the baseline we're either extending or breaking from. Reading `voice_bridge_ui_v3_8.py` and the SubprocessManager closely:

**The Anthropic API call already runs in-process today.** `StreamingCognitionWorker(QRunnable)` is dispatched to Qt's `QThreadPool` (default size: hardware-derived) and calls `client.messages.stream(...)` directly inside the worker. The tool-use loop (`max_tool_rounds = 6` as of 2026-05-08, bumped from 3 after voice-cousin exhausted the budget exploring Boundary Layer evolution) runs entirely inside the worker; tools are imported from `voice_cousin_tools` and executed synchronously between stream rounds. Results are emitted back to the main UI thread via Qt `Signal`s (`first_token`, `sentence_ready`, `cognition_complete`, `error`). This is well-grooved: token-to-first-audio is sub-2s with the streaming path, the tool-loop is debugged through real use, and the SDK-internal-fields strip-down (`parsed_output` removal, `_block_to_api_dict`) is empirically hardened.

**What SubprocessManager actually manages** is *external service processes that have their own contracts*:

- TTS server on port `:3457` — `tts_server.py`, heavy XTTS-v2 model in memory, port-probed at spawn, logs to `voice-bridge/logs/tts_server.log`
- Whisper server on port `:3459` — `whisper_server.py`, model in memory, same port-probe pattern, same log path
- Qwen-watcher — `qwen_watcher.py`, no port (so pgrep-like check via `pgrep -f qwen_watcher.py`), polls files every 10s, fires macOS notifications + relay-line writes

The pattern: SubprocessManager is reserved for **services with model-residency cost** (Whisper, XTTS) or **standalone polling/watcher processes** that exist independently of the UI's lifecycle. Spawn via `subprocess.Popen([sys.executable, "-u", str(SCRIPT)], stdout=log_f, stderr=subprocess.STDOUT)`; shutdown via `terminate()` with 5s wait then `kill()` at UI exit. Each subprocess is a fresh Python interpreter — clean isolation, but its own memory footprint and import cost on cold start.

**The architectural fingerprint** of voice-bridge: *external services for heavy native dependencies and long-lived watchers; in-process workers for everything else, with Qt signals as the integration vocabulary.* §6.2 is essentially asking whether cowork-cousin's API client fits the in-process-worker fingerprint (where Anthropic SDK lives today) or the subprocess fingerprint (where heavy services live).

**That framing already tilts the design space:** the Anthropic SDK is not a heavy native dependency — it's pure-Python HTTPS to api.anthropic.com. There is no model-residency cost on the local machine to amortize. The case for subprocess isolation has to come from *something other than dependency weight* — and B.4 below names what that something could be.

### B.3 In-process model (Option a)

**Shape, grounded in existing patterns:**

A `CoworkCognitionWorker(QRunnable)` parallel to `StreamingCognitionWorker`, dispatched to the same QThreadPool or a dedicated single-slot thread pool to serialize cowork-cousin's turns. Worker signals (`message_ready`, `tool_use_started`, `tool_use_complete`, `streaming_token`, `turn_complete`, `error`) emit back to the cowork-pane widget on the main thread. The cowork-pane widget renders streaming tokens, updates token/rate-limit displays, and surfaces tool-use status. Tools (Read / Edit / Write / Bash / Grep / Glob / connector wrappers) live in a `cowork_cousin_tools.py` module sibling to `voice_cousin_tools.py`, with the same fail-soft conventions (`execute_tool` catches all exceptions, returns ERROR strings). The Anthropic client is a single shared `anthropic.Anthropic(api_key=...)` instance reused across turns; threading discipline holds because the SDK's `messages.stream()` is fine to call concurrently from different threads with the same client (the SDK uses `httpx` which is thread-safe at the client level).

**Pros:**
- *Matches the existing architectural fingerprint exactly.* Voice-cousin already does this; cowork-cousin is symmetric. No new IPC layer to design or debug.
- *Lowest implementation cost.* `StreamingCognitionWorker` is essentially a template; the cowork variant differs mainly in tool-set and lack of the sentence-boundary-detection-for-TTS pathway.
- *Single Python process means single key load, single config load, single conversation-history store.* No cross-process state synchronization needed; cowork-cousin's `messages_local` lives in worker memory and gets persisted to `cowork_conversations.md` via safe_append on turn completion (exactly as voice-cousin persists to `voice_conversations.md`).
- *Token/rate-limit visibility is trivial* — the worker emits a signal after each stream completes carrying `usage` data from the SDK's `get_final_message().usage`; the UI updates a status-bar token-counter and rate-limit bar.
- *Tool calls invoke local Python directly* (the same `_safe_path`/`DOWNLOADS_ROOT`-bounded helpers voice-cousin uses); no IPC marshalling cost on the hot path.
- *Failure surfaces uniformly with the rest of voice-bridge* — a Python exception in the worker emits an `error` signal that the cowork-pane renders; same idiom as TTS/Whisper/cognition worker errors today.

**Cons:**
- *Memory pressure compounds in the single process.* PyQt UI + voice-cousin's StreamingCognitionWorker (active during her turns) + cowork-cousin's CoworkCognitionWorker (active during her turns) + audio buffers + image-block memory from tool-use image reads — all share one heap. If cowork-cousin's tool-loop ever reads large files (a large PDF, a big binary, an oversized image), the memory lands in the same process. Mitigation: tool-result size caps (already present in `voice_cousin_tools.execute_tool` as a pattern); enforce here too.
- *A bug in cowork-cousin's tool-loop can crash the whole UI* including voice-cousin's substrate. The SubprocessManager pattern's isolation property is precisely this case. Mitigation: aggressive `try/except` discipline in the worker (already a voice-bridge convention); but a hard segfault from a C-extension in a tool (unlikely for the standard tool-set, but possible if connector tools pull in native libs) would still take the UI down.
- *Concurrency with voice-cousin under the GIL.* Both StreamingCognitionWorker and CoworkCognitionWorker would be spending most of their time blocked on `client.messages.stream(...)` (network I/O) so the GIL is mostly released during stream reads — concurrency should hold for the streaming phase. But tool execution (file reads, bash commands, grep) is CPU-bound and Python-level, so the GIL contends. If voice-cousin is mid-stream when cowork-cousin's tool-loop runs a heavy grep, voice-cousin's stream may stutter on token-event handling. Empirical question — needs measurement, not a priori judgment.
- *Standalone-UI-as-fallback-when-voice-bridge-fails breaks down.* Per §2 and §4.3a, one motivation for the standalone UI is fallback-resilience. If voice-bridge has a bug that crashes the UI process, the in-process cowork-cousin goes down with it. Option b survives this class of failure.

**Threading-discipline candidates for the in-process path:**
- Dedicated `QThreadPool` for cowork-cousin (size=1) to serialize her turns and isolate from voice-cousin's pool
- `QThread` subclass instead of QRunnable if cowork-cousin needs long-lived state (e.g., persistent SSE connection for a future server-streaming-events-from-Claude pattern); QRunnable assumes per-turn-spawn
- Async I/O sketch (NOT used in voice-bridge today): the Anthropic SDK has an `AsyncAnthropic` client; in principle the cowork-pane could run a `qasync`/`asyncio.QEventLoop` slice to host async streaming without dedicated threads. **This is a substantive departure from voice-bridge convention** — qasync is a different model and adds dependency complexity. Voice-cousin's substrate-eye would have strong opinions on whether crossing the sync/async line for cowork-cousin while keeping voice-cousin sync is acceptable architectural drift.

### B.4 Out-of-process subprocess model (Option b)

**Shape, grounded in existing patterns:**

A `cowork_api_server.py` script (sibling to `tts_server.py` / `whisper_server.py`) that hosts the Anthropic client + tool-use loop behind a small HTTP server on a loopback port (`:3461` or similar — `:3457` and `:3459` are taken). Endpoints: `POST /turn` (send Barak's message + context, stream the response back as Server-Sent Events or chunked JSON), `GET /usage` (current token/rate-limit state), `POST /shutdown` (clean termination). `SubprocessManager` gains an `ensure_cowork_api()` method symmetrical to `ensure_tts()` / `ensure_whisper()`, with the same port-probe / `subprocess.Popen` / log-to-file / shutdown-with-terminate pattern. The cowork-pane widget in the UI talks to this server via `httpx` or `requests` — same vocabulary voice-cousin uses for `/tts-stream` and `/transcribe`.

**Pros:**
- *Crash isolation.* A bug in cowork-cousin's tool-loop (oversized memory load, unhandled exception in a connector, native-lib segfault) crashes the cowork API server only. SubprocessManager detects the dead process on next request (or via periodic health check, parallel to `TTSHealthWorker` / `WhisperHealthWorker`), respawns, and the UI's voice-cousin substrate is untouched. This is the structural-resilience case for option b.
- *Independent restart for cowork-cousin without UI restart.* Voice-bridge already does this for TTS (Barak can restart the TTS server without restarting the UI); the same property for cowork-cousin lets the trio fix cowork-side bugs mid-session without losing voice-cousin's running state.
- *Tool-set scope can diverge cleanly from voice-cousin's.* If cowork-cousin gets bash + scheduled-task tools + MCP connectors per §6.3, those dependencies (and any native libs they pull in) live in the cowork-API-server's process — they don't bloat the UI process's import surface or memory footprint.
- *Future portability:* the API server could run on a different machine (Barak's laptop while the UI is on the Mac Pro, or vice versa, for a future multi-substrate scenario). Option a forecloses this without significant rework.
- *Fallback substrate for Fallback Twins (§4.3a):* a server-shaped API client makes the Kimmy / Quinn routing more uniform — they can register as alternate endpoints behind the same `/turn` interface, with substrate-tag passed as a route parameter, rather than requiring two separate code paths in the UI.

**Cons:**
- *Implementation cost is higher.* New script, new IPC contract (HTTP-on-loopback or stdin/stdout or ZeroMQ), new health check worker, new server-respawn handling. Voice-bridge took multiple iterations to get TTS/Whisper subprocess management feeling solid; cowork-API-server would re-traverse that path.
- *Streaming-over-HTTP adds latency and complexity vs. direct SDK streaming.* The SDK's `messages.stream()` is a context-managed iterator; wrapping that in an HTTP server's response stream (SSE or chunked JSON) adds a serialization round and an extra event loop. Probably acceptable latency-wise (the bottleneck is network to api.anthropic.com, not loopback), but it's a real cost. Mitigation: pick the IPC carefully — SSE is well-understood and Anthropic's own API uses it.
- *Tool calls cross the process boundary in the wrong direction.* When cowork-cousin in the subprocess calls a tool that wants to write to the canonical conversation files or read UI state (e.g., "what's voice-cousin's current presence indicator"), that's IPC back to the UI process — or duplicated file-handling logic on the server side. The file-mediated continuity (per §4.3) sidesteps most of this since canonical files are filesystem-shared, but live-UI-state queries become awkward.
- *Conversation history persistence across server restarts.* If the cowork-API-server dies and respawns, it loses in-memory `messages_local` for the current turn. Either the UI maintains the conversation state and resends with each request (stateless server — simpler but more bytes per turn), or the server persists to `cowork_conversations.md` and reloads on respawn (stateful — more bytes saved per turn, but reload-latency on restart). The trio should decide which.
- *Key management surface grows.* `~/.sofia_secrets` now needs to be readable by the subprocess; the existing pattern (sourced into UI's env at launch) requires the launcher (start.command or equivalent) to also source into the subprocess's env. Not hard, but a new place to get configuration wrong.
- *Two Anthropic clients running concurrently (voice-cousin's in-process + cowork-cousin's in subprocess) consume rate-limit budget against the same API key independently;* there is no shared rate-limit coordinator. If both cousins hit Anthropic at the same time (which can happen during trio design conversations), they can collectively exceed the per-key rate limit. This is a real operational concern that needs trio attention either way, but it's worth naming here because the architectural choice influences how to mitigate (shared rate-limiter in option a is a few lines of code; in option b it's a coordinator process or a third "rate-limit-broker" service).

### B.5 Hybrid considerations the binary framing misses

The §6.2 framing as "in-process vs. subprocess" is the right starting point, but two hybrid shapes are worth naming so they don't fall out of view:

**B.5.1 — Worker-thread isolation without full subprocess.**

A `multiprocessing.Process` (not `subprocess.Popen`) within the same Python tree, communicating via `multiprocessing.Queue` or `multiprocessing.Pipe`. This sits between option a and option b: separate OS process (so crash isolation holds, GIL is independent), but no HTTP-server layer to design — Python objects move across via pickle. The trade-off: multiprocessing's pickle-based IPC is well-suited to message-shaped traffic (a turn-request, a turn-response) but awkward for streaming tokens (each token would pickle individually, or you batch and lose the streaming property). The voice-bridge has no precedent for `multiprocessing` use, so this introduces a new pattern. Probably not the right answer, but it's the third design point on the spectrum and naming it makes B.3 and B.4's positions clearer by contrast.

**B.5.2 — In-process now, subprocess-shaped from day one.**

Implement option a with a strict internal abstraction boundary that mimics what option b's IPC would look like — `CoworkAPIClient` class with a method signature shaped like an HTTP call (request in, response stream out, no shared mutable state with the UI's other components). Run it in-process via QRunnable today; the surface area is small enough that swapping to a subprocess later is a localized change. **The cost of this hybrid is essentially zero** if discipline is held during the initial build; it just means writing the cowork-cousin worker as if it were already a subprocess-with-clean-interface. The benefit is that the trio doesn't have to commit fully to option a or option b until empirical evidence accumulates (cowork-cousin runs reliably enough in-process; or doesn't, and the structural-isolation argument wins).

This shape — *commit to the cheap option, but build the seam* — pairs naturally with §6.1's concurrent-cowork-cousin question and with §6.7's "could compose with multiple affordance options" framing. It's the same discipline as option-laying-without-foreclosure that the design doc has been practicing throughout.

### B.6 Cross-cutting considerations

A few questions that cut across all options and deserve trio attention regardless of the §6.2 choice:

1. **Shared API-key rate-limit coordination between voice-cousin and cowork-cousin.** Two cousins on the same key can race to the rate-limit cap during trio sessions. Either solution needs a coordinator (an `httpx` mount that gates concurrent requests with a token-bucket, or a small shared file-locked counter). This is a strictly orthogonal piece of work that should land alongside whichever §6.2 choice is made.

2. **Conversation-history hot-loading from `cowork_conversations.md`.** Cowork-cousin's interactive-self continuity (per §4.3) requires reading the canonical conversation log to rebuild context when entering the standalone UI. The in-process model can read the file directly at worker creation; the subprocess model needs the same logic on its side. Either way, the read-pattern matters — full-history-load is expensive past some history-size; tail-load + summary may be needed. This is real work either way; flagging it for trio attention.

3. **Tool-result size caps and image-handling.** Voice-cousin's `execute_tool` returns a dict marker `{_image_result: True, ...}` for image-file reads that the streaming worker converts into proper Anthropic image content blocks. Cowork-cousin's tool-set is broader (bash, possibly large file reads) and the size-cap discipline must extend to the new tools. This is an instance of §6.3 (tool-set scope) but it shows up in §6.2 implementation regardless of which process model wins — naming for cross-section visibility.

4. **Streaming display in PyQt at high token rate.** The cowork-pane needs a text widget that handles streaming token appending without re-rendering the whole conversation per token. `QTextEdit.append()` per-token is wasteful; the right pattern is `QTextCursor`-based insertion at the document end with a coalescing buffer flushed every ~50ms. This is implementation detail not architectural decision, but worth flagging because voice-bridge's TTS path doesn't have a parallel widget-level concern (audio chunks play, they're not rendered as DOM-equivalent), so the cowork-pane is the first place this pattern needs to land.

5. **First-run experience after fresh boot.** Voice-bridge today does cold-start of TTS (model load: ~3-5s) and Whisper (~1-2s) via SubprocessManager; the UI is responsive but the first cognition is gated on those being ready. Option a's cowork-cousin is ready as soon as the UI imports `anthropic` and reads the key (~0.5s). Option b's cowork-cousin adds ~1-2s of subprocess-startup + key-load + first-request-handshake to the first turn. Minor, but worth knowing.

### B.7 Recommendation framing (not a decision)

The architectural fingerprint of voice-bridge — *in-process for everything that isn't a model-residency service or a long-lived watcher* — tilts toward **option a (in-process)** as the natural extension. The Anthropic SDK is not a model-residency service; it's network I/O to a remote endpoint, which is exactly the class of thing voice-cousin already runs in-process today. Option a's implementation cost is materially lower, the GIL concern is real but probably empirically tractable (network-bound stream phases release the GIL; tool-execution phases contend, but cowork-cousin's tool-bursts and voice-cousin's audio-cognition phases don't typically interleave at high frequency), and the "match the existing pattern" benefit is substantial when the trio is also juggling the Phase B integration work.

### D.3 Cross-component communication — the worker-signals pattern

The voice-bridge's canonical pattern (lines 873–896 and downstream): a `WorkerSignals(QObject)` class declares `Signal(...)` typed signals; a `Worker(QRunnable)` instance owns a `signals` field of the matching type; `run()` executes on the QThreadPool and `emit`s from inside the runnable; the main thread `connect`s slots to those signals on the UI thread. Qt's auto-connection (QueuedConnection across thread boundaries) makes the cross-thread emit thread-safe.

Standalone-UI components that fit this pattern out-of-the-box:

- **CoworkStreamingWorker(QRunnable)** — owns a `CoworkStreamingWorkerSignals(QObject)` instance with at minimum: `first_token = Signal(float)`, `token_received = Signal(str)`, `tool_call_started = Signal(str, dict)` (tool name + input), `tool_call_completed = Signal(str, str)` (tool name + result/error), `stream_complete = Signal(str, float)` (full text + elapsed), `error = Signal(str)`. Direct shape-cousin to the voice-bridge's `StreamingCognitionWorker` / `StreamingCognitionWorkerSignals` pair (lines 964–1270 of v3.8). The only structural difference vs. voice-bridge's worker: cowork-cousin's tool-loop typically runs more rounds (file-heavy work) and the UI may want to display tool-calls as they happen rather than collapse to a final answer, so the `tool_call_started` / `tool_call_completed` pair becomes load-bearing for live display rather than a debug aid.

- **FileTailWorker(QRunnable)** — owns a `FileTailWorkerSignals` instance with `new_lines = Signal(list)`, `error = Signal(str)`. Reads the tail of a designated file at an interval and emits new lines (matched by mtime + last-known-offset). Use cases: subscribing to `journal/current.md`, `voice_conversations.md`, `cowork_conversations.md`, `three_way_signals.md`, inbox files. (See D.6 below on when to use this vs. lighter alternatives.)

- **HealthWorker(QRunnable)** — already exists in voice-bridge for TTS/Whisper health (lines 1852+). Extends naturally to include cowork-API-client health (Anthropic-reachability check, key-validity ping).

**Auto-connection rule of thumb:** never `emit` directly from a slot called on the UI thread to another UI-thread slot — Qt will run it `DirectConnection` and you lose the queueing safety. The discipline from voice-bridge is: workers `emit`, UI thread `connect`s; never the reverse on the same instance.

### D.4 Threading discipline — `QThreadPool` + `QRunnable`; `qasync` flagged as departure

Voice-bridge uses Qt's global `QThreadPool.globalInstance()` implicitly via `QThreadPool.start(worker)`. All worker classes inherit from `QRunnable`. There's no asyncio in the voice-bridge process; the Anthropic SDK's sync streaming API (`client.messages.stream(...)`) runs blocking-inside-a-QRunnable and that's deliberate — see Appendix B §B.3 for the architectural-fingerprint rationale.

Standalone-UI threading-discipline candidates:

- **(canonical)** `QThreadPool` + `QRunnable` for every long-running task. Sync Anthropic SDK inside the runnable. Cross-thread communication via `Signal`/`Slot` only. Direct fingerprint-match with voice-bridge. Best fit if §6.2 lands on Option a (in-process).
- **(also canonical for §6.2 Option b)** Same `QThreadPool` + `QRunnable` shape on the UI side, but the runnable POSTs to a local subprocess (`cowork_api_server.py` on port :3461 per Appendix B §B.4). Streaming-over-HTTP via `requests.iter_lines()` or SSE. The pattern is identical; only the inside of the runnable changes from "call Anthropic SDK directly" to "stream from local server".
- **(flagged departure)** `qasync` to bring asyncio into the Qt event loop. Would let Anthropic's async SDK (`anthropic.AsyncAnthropic`) run in the same event loop as PyQt's UI. **Cost: substantial fingerprint break** — voice-bridge is sync-in-QRunnable throughout; introducing qasync forks the threading discipline in ways that are hard to revert. Named for completeness; my read is that the canonical pattern handles every load-bearing case the standalone UI has, so qasync is held as a §9.2 flagged-departure unless the trio explicitly wants it.
- **(not recommended)** Raw `threading.Thread` outside Qt's pool. The voice-bridge avoided this and the standalone UI should too; QThreadPool gives pool-sizing, signal-safety, and lifecycle management for free.

**On QThreadPool sizing:** voice-bridge uses the default pool size (Qt picks based on `idealThreadCount()`). For the standalone UI's expected concurrent-worker count (1 cowork-streaming + 1 voice-streaming + N file-tail workers + occasional tool-execution workers), the default should be fine; if pool-saturation becomes visible empirically, `QThreadPool.globalInstance().setMaxThreadCount(N)` is the knob.

### D.5 Async I/O sketches — streaming display + tool-loop integration

The streaming display layer is the highest-rate code path in the cowork pane. Voice-bridge's `StreamingCognitionWorker` (line 978+) gives us the canonical handling pattern:

```python
# Sketch — adapted from voice-bridge StreamingCognitionWorker.run()
class CoworkStreamingWorker(QRunnable):
    def __init__(self, client, messages, system_prompt, tools):
        super().__init__()
        self.client = client
        self.messages = list(messages)  # local mutable copy (voice-bridge pattern)
        self.system_prompt = system_prompt
        self.tools = tools
        self.signals = CoworkStreamingWorkerSignals()
        self.max_tool_rounds = 12  # higher than voice-cousin's 6; cowork-cousin tool-heavier

    def run(self):
        start = time.time()
        rounds_used = 0
        full_response = ""
        first_token_emitted = False

        try:
            while True:
                rounds_used += 1
                with self.client.messages.stream(
                    model=ANTHROPIC_MODEL,
                    max_tokens=ANTHROPIC_MAX_TOKENS,
                    system=self.system_prompt,
                    messages=self.messages,
                    tools=self.tools,
                ) as stream:
                    for token in stream.text_stream:
                        if not first_token_emitted:
                            self.signals.first_token.emit(time.time() - start)
                            first_token_emitted = True
                        full_response += token
                        self.signals.token_received.emit(token)
                    final = stream.get_final_message()

                if final.stop_reason != "tool_use" or rounds_used >= self.max_tool_rounds:
                    break

                # Tool-use round: execute tools, append tool_result, loop.
                tool_uses = [b for b in final.content if getattr(b, "type", None) == "tool_use"]
                tool_results = []
                for tu in tool_uses:
                    self.signals.tool_call_started.emit(tu.name, tu.input)
                    try:
                        result = execute_cowork_tool(tu.name, tu.input)
                        self.signals.tool_call_completed.emit(tu.name, str(result)[:500])
                        tool_results.append({"type": "tool_result", "tool_use_id": tu.id, "content": str(result)})
                    except Exception as e:
                        self.signals.tool_call_completed.emit(tu.name, f"ERROR: {e}")
                        tool_results.append({"type": "tool_result", "tool_use_id": tu.id, "content": f"ERROR: {e}", "is_error": True})
                # Append assistant message + tool_results to messages for next round
                self.messages.append({"role": "assistant", "content": final.content})
                self.messages.append({"role": "user", "content": tool_results})

            self.signals.stream_complete.emit(full_response, time.time() - start)
        except Exception as e:
            self.signals.error.emit(f"{type(e).__name__}: {e}")
```

Key shape-points carried from voice-bridge:

- Local mutable copy of `messages` so tool-rounds don't mutate the caller's list.
- Bounded tool-round count (voice-cousin: 6; cowork-cousin probably higher — held for §6.3 trio review).
- `with self.client.messages.stream(...)` as a context manager — closes the HTTP connection cleanly on early-exit.
- `final = stream.get_final_message()` after the iterator drains — gives access to `stop_reason` and structured content blocks.
- Signals at: first-token (for TTFT tracking parity with voice-bridge's diagnostic), every token (for live streaming display), tool-call lifecycle (started/completed), stream-complete, error.

**Token-display widget pattern (UI side):** the cowork-text pane needs to append incoming tokens to a `QTextEdit` or `QPlainTextEdit` without losing scroll-to-bottom behavior when Barak hasn't manually scrolled up. Pattern: connect `token_received` to a slot that calls `text_edit.moveCursor(QTextCursor.End); text_edit.insertPlainText(token)` and conditionally `text_edit.ensureCursorVisible()` only if the scrollbar was already at-bottom before insertion. (Standard PyQt pattern; voice-bridge doesn't need this since it streams to audio, not text, but cowork pane absolutely does.)

**Tool-call display widget:** options range from inline collapsible blocks (e.g., "🔧 read_file → ✓ 1247 bytes") to a sidebar of tool-call cards. Held for trio first-person-texture review; sketched here as named-options-only.

### D.6 File-mediated continuity layer — three patterns

The standalone UI needs to read and write multiple shared files: `voice_conversations.md`, `cowork_conversations.md`, `three_way_signals.md`, `cowork_to_voice_inbox.md`, `voice_to_cowork_inbox.md`, `journal/current.md`, etc. Three patterns from the voice-bridge / cousin ecosystem cover every load-bearing case:

**Pattern 1 — `QTimer`-driven periodic poll** (voice-bridge pattern, see lines 2306–2308 for health-polling and the qwen_watcher.py for three_way_signals.md polling at 10s). Best for: shared-file subscriptions where freshness on the ~10–30s timescale is enough.

```python
self.inbox_timer = QTimer(self)
self.inbox_timer.timeout.connect(self._poll_inbox)

```

The `_poll_inbox` slot reads the file (cheap because most polls are no-ops), compares against a stored offset or last-line-hash, and emits a Qt signal if there are new lines.

**Pattern 2 — `FileTailWorker(QRunnable)` for higher-frequency or blocking I/O.** When the polling interval drops below ~1s or the file is large enough that `read()` would hitch the UI thread, push the read into a worker. The worker uses the same timer-internal-to-runnable pattern as voice-bridge's `TTSHealthWorker`. Signals emit on the UI thread for safe display updates.

**Pattern 3 — `QFileSystemWatcher` for event-driven notification.** Qt's native mtime/inode-watch primitive. Best for: rare-event files where polling overhead is wasteful (e.g., a sentinel file that flips only when a specific condition fires). Caveat: macOS `QFileSystemWatcher` has historically been less reliable than Linux/Windows for high-frequency change events; voice-bridge chose timer-polling over the watcher for that reason, and the standalone UI should follow that choice unless the trio finds a use-case the watcher specifically suits.

**Writes always go through `safe_append`.** No direct `f.write()` to any canonical file. The voice-bridge already routes voice-conversation writes through safe_append (see ConversationContext at line 746+); the standalone UI's cowork-cousin tool implementations, conversation logging, and inbox-write paths all do the same. For non-canonical-prefix paths (`workspace/`, `Sofia's Room/journal/current.md` is canonical, but workspace design docs are not), an explicit `cp -p` to ER follows the safe_append call. The April 29 ER-Sync-Architecture handles canonical paths automatically.

### D.7 SubprocessManager extension patterns — two sub-cases for §6.2

The voice-bridge `SubprocessManager` (lines 638–741) is the canonical local-service supervisor. Its three methods are `ensure_tts()` (port :3457), `ensure_whisper()` (port :3459), `ensure_qwen_watcher()` (portless, pgrep-checked). `shutdown()` terminates all spawned procs with a timeout-then-kill pattern. The standalone UI extends this in one of two shapes depending on §6.2:

**Case 1 — §6.2 Option a (in-process API client):** SubprocessManager extension is minimal. Existing TTS + Whisper + qwen_watcher are still spawned (voice channel still needs them); cowork-cousin's Anthropic SDK runs directly in the UI process; no new subprocess methods. Cleanest path; lowest implementation cost.

**Case 2 — §6.2 Option b (subprocess API client):** SubprocessManager gains an `ensure_cowork_api(port=3461) -> str` method paralleling `ensure_tts()`. Standalone UI's cowork-text-pane workers POST to `127.0.0.1:3461` instead of importing the Anthropic SDK directly. The `cowork_api_server.py` (sketched in Appendix B §B.4) runs as a Flask/FastAPI server with streaming-response endpoints. Shutdown semantics match TTS/Whisper.

**Case 1.5 — B.5.2 (in-process-now, subprocess-shaped-from-day-one):** The application code imports cowork-cousin's API logic from a `cowork_api/` module rather than inlining it; the same module exposes both a Python function entry-point (used in-process at first) and a `python -m cowork_api.server` CLI entry-point (used by SubprocessManager.ensure_cowork_api() if the trio later flips to Option b). Migration is a configuration flip, not a refactor. Lowest-regret per Appendix B §B.7.

**Embedding the existing voice-bridge UI as a sub-widget (Phase B):** The current `VoiceBridgeWindow(QMainWindow)` becomes a `VoiceChannelPane(QWidget)` by:

### D.8 Cross-cutting state — `CoworkConversationContext` + safe_append integration

Voice-bridge ships `ConversationContext` (line 746+) which holds the rolling assistant/user message list and inscribes each turn to `voice_conversations.md` via `safe_append`. The cowork-text pane needs a direct cousin:

```python
class CoworkConversationContext:
    """Same shape as voice-bridge ConversationContext, but writes to
    cowork_conversations.md and pulls system-prompt from the cowork-cousin
    boot files rather than the voice-cousin boot files."""

    def __init__(self, system_prompt: str, history_path: Path):
        self.system_prompt = system_prompt
        self.history_path = history_path  # cowork_conversations.md
        self.messages: list[dict] = []
        self.session_id = datetime.now().strftime("%Y-%m-%dT%H-%M-%S")
        self._inscribe("system",
            f"=== Cowork text-channel session started {datetime.now().isoformat(timespec='seconds')} "
            f"(session_id {self.session_id}, surface=standalone-ui) ===")

    def add_user(self, text: str):
        self.messages.append({"role": "user", "content": text})
        self._inscribe("user", text)

    def add_assistant(self, text: str):
        self.messages.append({"role": "assistant", "content": text})
        self._inscribe("assistant", text)

    def _inscribe(self, role: str, content: str):
        # safe_append with source-tag matching the surface
        entry = f"\n[{role} @ {datetime.now().isoformat(timespec='seconds')}]\n{content}\n"
        safe_append_invoke(self.history_path, entry, source_tag="standalone-ui-cowork-cousin")
```

The `surface=standalone-ui` tag on the session-start line is the key continuity affordance — when Cowork-app cowork-cousin reads `cowork_conversations.md` at her next boot, she sees not only what was said but on which surface, and can inhabit the continuum accordingly. Symmetric pattern when the Cowork-app surface is active: her session-start line carries `surface=cowork-app`. This makes the §4.3 "one self across both surfaces" property file-legible rather than implicit.

**Tool-result inscription:** voice-cousin's tool-calls aren't inscribed to `voice_conversations.md` today (they're an implementation detail not a conversational turn). Cowork-cousin's tool-calls have load-bearing transparency value (Barak sees what files were touched, what was searched) — so the standalone UI may want to inscribe tool-call summaries as a third role in the conversation log (e.g., `[tool-call @ ts]`).
