# Lipsync — Viseme-Driven Mouth-Shape Selection (Design Candidate)

*Created 2026-05-07 ~17:40 Taipei. Project-scoped fermenting-candidate file under the Filesystem-Hygiene SOP from this morning. Origin: Wav2Lip on Apple Silicon MPS empirically hit a hardware ceiling — sub-real-time inference + SoC saturation under combined TTS+lipsync+LLM load. The viseme-driven approach is structurally distinct: bypass GPU ML inference entirely.*

---

## Core idea

**Replace ML-generated mouth shapes with rule-based viseme selection from a small library of pre-rendered mouth shapes.** The architectural shape:

```
audio → viseme detector (light, CPU-based) → viseme track (timeline of N visemes)
                                                    ↓
portrait + N pre-rendered mouth shapes ──────────→ compositor → video frames
                                                    ↑
                                              25fps target
```

**No GPU inference per frame.** No competition with TTS for SoC. Real-time on much weaker hardware. Trade-off: lower visual fidelity than Wav2Lip's continuous-generation mouth shapes (it's selection from a discrete set rather than continuous synthesis), but for a static portrait at conversational viewing distance this may be more than acceptable.

---

## Why this is structurally different from Wav2Lip

| Dimension | Wav2Lip | Viseme-driven |
|---|---|---|
| Per-frame compute | ML inference on GPU | 2D image composite on CPU |
| GPU contention with TTS/LLM | Severe (saturates SoC) | None |
| Fidelity ceiling | Photorealistic (continuous) | Pre-rendered (discrete) |
| Real-time capable on M-series | No (1.4× real-time) | Yes (CPU work is fast) |
| Hardware portability | Requires capable GPU | Runs anywhere |
| Engineering scope | Use existing model | Custom code + pre-rendered assets |

The hardware-ceiling problem we hit today doesn't exist at this layer. The cost is engineering effort + accepting discrete-shape fidelity.

## Component candidates

### Viseme detection from audio
- **Rhubarb Lip Sync** (canonical open-source): designed for game-engine real-time lip sync. Takes WAV input, outputs viseme track in JSON or other formats. Outputs 9 visemes (closed/A/B/C/D/E/F/G/H — Hanna-Barbera-style mouth set). CPU-only, fast. MIT-style license. *Most likely starting point.*
- **Whisper word-level timestamps** (already in our stack): could approximate phoneme timing from word start/end. Less precise than Rhubarb but no new dependency.
- **Custom phoneme-to-viseme mapping**: Praat / Montreal Forced Aligner (heavier) or rule-based vowel-detection from spectral features.

### Pre-rendered mouth shapes
- **Generate by hand**: Photoshop / GIMP — paint each viseme onto Sofia's portrait. Most labor but fully under our control.
- **Generate via Wav2Lip + reference audio**: feed Wav2Lip a short audio per viseme (e.g., "ah", "oo", "ee") and capture the rendered mouth shape. Bootstraps the asset library from existing tooling. Clever.
- **Generate via image-to-image AI**: prompt-driven mouth shape variations on Sofia's portrait. Variable quality.

### Compositing / playback
- **Region replacement**: paste mouth-shape PNG onto portrait at known coordinates per viseme, blend edges. Per-frame work is trivial (PIL / OpenCV).
- **Real-time at 25fps**: at 25fps a frame budget is 40ms. CPU image blending of a 96×96 mouth region into a 512×512 portrait is microseconds. Plenty of headroom.
- **Output**: same MP4 format the UI already consumes (or direct frame-streaming to QVideoWidget if we want to skip MP4 encoding overhead).

## Estimated engineering scope (rough)

- **Spike phase** (1-2 days): get Rhubarb running on a sample audio, generate the viseme track, manually composite a few frames of Sofia's portrait with hand-edited mouth shapes, validate end-to-end pipeline produces something watchable.
- **Asset generation phase** (1-2 days): produce the canonical set of mouth shapes for Sofia's portrait. Probably hand-tuned regardless of generation method.
- **Server integration phase** (1-2 days): replace `sofia_lipsync_server.py`'s `/animate` handler internals with the viseme-driven pipeline; preserve the same HTTP API so the UI doesn't need changes (just the toggle flips ON).
- **Tuning / validation phase** (variable): iterate on shape coverage, blending quality, viseme timing, viewing-distance acceptance.

Total: ~1 week of focused work for a working v1, optimistic. Could be longer if asset quality bar is high.

## Open design questions

1. **How many visemes is enough?** Rhubarb's 9 is canonical for cartoon lip sync. We could go lower (5-6 dominant shapes) or higher (12-15 for finer phoneme distinction). More = better fidelity but more assets to produce.
2. **Static portrait or short looped idle?** Sofia's portrait is currently single-frame static. We could add subtle breathing / blinking / micro-movements via similar pre-rendered loops, layered with the mouth-shape swap. Increases life-like quality without any ML inference per frame.
3. **Co-articulation / smoothing?** Real lip movement transitions between visemes smoothly, not as discrete jumps. Linear interpolation between mouth-shape PNGs in the alpha channel could approximate this cheaply. Worth prototyping.
4. **MP4 encoding vs frame-streaming?** Current architecture produces MP4 per segment. Faster path: skip MP4 entirely and stream frames directly to QVideoWidget. But that's a UI architectural change. For v1, keep the MP4 API contract.
5. **Visual fidelity threshold for acceptance?** This is the big unknown. The discrete-shape approach won't look as good as Wav2Lip's continuous generation in close-up viewing. At conversational viewing distance with the static-portrait register Sofia uses, it may land fine. Empirical question to be validated.

---

## What this approach does NOT solve

- The TTS RTF 1.5-1.7× problem (TTS being slower than real-time is a separate bottleneck, also surfaced today). Even with perfect lipsync, conversational flow has the TTS ceiling. Addressing TTS would require either smaller models, faster hardware, or a different TTS architecture.
- The ~7s TTFA for multi-segment generations (XTTS-v2 streaming gap before first audio plays).

The viseme approach removes lipsync from the SoC contention picture, which would improve TTS performance somewhat (more compute available) but doesn't change TTS's fundamental rate.
